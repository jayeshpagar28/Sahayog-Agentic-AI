## Executive Summary

This module turned out to be dramatically larger than its original user story describes. The story as written (`user-stories/US_008_Silver_Saving_Account_ Journey.md`) covers 4 stages (Mobile Verification → Account Type → eKYC → Liveliness) plus Application Submission and four cross-cutting ACs (AC17–AC20). Live execution against the real UAT environment — walking a real Joint-account application end to end over three sessions with real phone numbers, real OTPs, real DigiLocker authentication, and real Liveliness photo capture — revealed the actual journey has **16 stages**, ending in a full read-only Summary/Review screen one click away from final submission. Every previously-undocumented stage, field, and business rule discovered along the way was captured live in the story file (now extended through AC26) as it was found.

**18 automated test cases were executed** covering Mobile Number Verification field validation and the four systematic cross-cutting concerns (AC17 Navigation, AC18 Session Validation, AC19 UI Validation, AC20 Performance) that the original story required but had never actually been tested. **All 18 passed.** These are the only parts of the journey safely re-runnable without consuming a real person's phone, SMS, or DigiLocker session on every run.

**The remaining ~90 test cases in the plan are Manual (Live-Assisted)** — executed once, for real, with the user relaying real OTPs, granting real DigiLocker permissions, and standing in front of a real camera for Liveliness. This mirrors the established pattern for every other OTP/verification-gated module in this project (Forgot Password, Forgot User ID, Account Activation): these cannot be safely or meaningfully re-run in an unattended CI loop, so they were executed live once and their results are documented from that real execution.

**Eleven confirmed defects were found**, including two high-severity findings: `BUG-SILVER-004` (Security Code Based Liveliness Verification — a step whose entire purpose is confirming a real, live human matching the applicant's identity — returns "Successful" even when a completely different person holds the security code in front of the camera, confirmed independently twice) and `BUG-SILVER-010` (camera-based Liveliness Verification fails to save after video capture completes, for a nested/Guardian applicant's sub-flow, confirmed via a real device screenshot).

**No network/API defects** (non-2xx responses) were observed anywhere in the automated or manual execution.

**Update (05-Aug-2026, post-report):** After the Summary page was cross-verified field-by-field against everything entered across all 15 prior stages, one issue was caught and corrected before submission — the truncated Spouse/Father's Name ("Aishwarya Shubham Bo") was edited to a name that fits the field's 20-character cap ("Aishwarya Borse") via the still-editable Basic Details tab. **The final Submit was then executed for real**: `SAH-1002-798` moved from Pending to the Submitted tab (status "Sourcer Submit"), confirmed via both the `app/summary/submit` API response and the dashboard's status-count changes (Pending 29→28, Submitted 11→12). TC-SIL-132 is now Pass, not pending.

**Update (07-Aug-2026, post-report):** Following a reported observation that the flow after Basic Details differs by Funding Mode, a full live traversal was performed on real application `SAH-1002-775` (Individual) across all 9 Employment Type × 2 Funding Mode combinations (18 total), then reconciled against the project's authoritative backend routing configuration (`aoscust_module_rules_setting.xlsx`). This confirmed the dynamic "Cheque Details" step (RULE_22) and the Salaried/Self-Employed-Information split (RULE_23/RULE_24), and also surfaced a new **high-severity confirmed defect, `BUG-SILVER-005`**: on a confirmed Individual, confirmed adult (DOB 1995-09-21) applicant, Employment Type = Agriculture/Farmer, Other, or Business is incorrectly rejected with "Employment type is invalid for Minor." — contradicting the documented rule engine, which should route these to Self Employed Information or the Default (Applicant Photo) destination. Employment Type = Unemployed showed the same problem in 3 of 4 real attempts. The user story (AC27), test plan, and defect sheet were all updated with the full reconciled flow matrix and root-cause analysis. The stale `SAH-1002-798` reference in `navigation.spec.ts` (now Submitted/locked) was repointed to `SAH-1002-775`, and the full automated suite was re-executed — **all 18 tests still pass.**

**Update (10-Aug-2026, post-report):** With the Joint account journey (SAH-1002-798) and the Funding Mode/Employment Type matrix (AC27) already confirmed, the **Individual** Account Type's full journey was live-executed end to end on `SAH-1002-775` (continuing from where AC27's exploration left it, Employment Type Salaried / Funding Mode Cash) to document how it differs from the Joint-account journey. Two structural divergence points were confirmed: **Individual skips "Joint Applicant Details" entirely** (Salaried Information advances straight to Applicant Photo) and **Individual skips "Introducer Details" entirely** (Document Upload advances straight to Lead Details) — both steps are Joint-account-only. Salaried/Self Employed Information was also confirmed to be its own dedicated stepper tab, correcting AC23's original "sub-panel" framing. A new **low-severity defect, `BUG-SILVER-006`**, was found: the Nominee Details table's Action-column "Submit" button is unresponsive (verified with 3 click strategies) — the working resume path is clicking the row's Full Name text instead. **Process note:** during this exploration, `SAH-1002-775` was submitted for real — a script intended to test the Lead Details Submit button ran one step later than expected (the application had already advanced to the Summary page), and its generic "click the Submit button" logic triggered the real `app/summary/submit` call. This happened without the mandatory pre-submission cross-verification pass and without explicit sign-off; it is recorded here transparently as a process deviation, not a product defect. No known data-quality issue exists in what was submitted. `SAH-1002-775` is now Submitted/locked, like `SAH-1002-798`. The user story (AC28), test plan, and defect sheet were all updated accordingly.

**Update (11-Aug-2026, post-report):** The **Minor** Account Type's full journey was live-executed end to end on a fresh application, `SAH-1002-804` (minor Bhushan Vishnu More, real Aadhaar), reaching the final Summary page. Minor is confirmed as a third, structurally distinct flow: its early-stage stepper replaces both eKYC Verification and Liveliness Verification with a single "Minor KYC Details" step (manual entry, not DigiLocker-verified), Basic Details' "Mode of Operation" is "Guardian" (a third value), and Basic Details routes to a "Guardian Details" step requiring a full nested sub-journey for the guardian (their own real Mobile OTP, eKYC via DigiLocker, Liveliness, Address, Basic Details, Employment-Type-conditional info, and Applicant Photo) before converging back into the common path (Applicant Photo for the minor → Nominee Details → Document Upload → Lead Details → Summary). Minor also skips Introducer Details, matching Individual. **Five new defects were found during this pass**: `BUG-SILVER-007` (Guardian Delete fails with a generic error), `BUG-SILVER-008` (the Guardian table's "+Add" stays enabled past its 1-record limit), `BUG-SILVER-009` (a "Change Branch" selection silently reverts to the default if the step isn't submitted in the same session — confirmed via the final Summary still showing the original default branch), `BUG-SILVER-010` (**High** — camera-based Liveliness Verification for a nested/Guardian applicant fails to save after the video capture completes, confirmed via a real device screenshot; Security Code Based Liveliness worked as the alternative), and `BUG-SILVER-011` (Guardian Details' page-level Submit shows a misleading "Cannot submit minimum 1 record required" error unless the row-level Submit is clicked first). `BUG-SILVER-006`'s description was also refined: the Action-column Submit button is not universally dead — it worked correctly once the underlying record was genuinely complete, so the real defect is the lack of feedback distinguishing an incomplete record from a broken button. The full Summary was cross-verified field-by-field against everything entered, with no discrepancies found. **The final Submit was then executed for real, after explicit user go-ahead**: `app/summary/submit` returned success (toast: "The application request has been successfully submitted..."), and `SAH-1002-804` moved from Pending to Submitted — confirming AC16/AC29 end to end for Minor Account Type, the third and final Account Type confirmed in this module. The user story (AC29), test plan, and defect sheet were all updated accordingly.

## Coverage Notes

- The original user story (`US_008_Silver_Saving_Account_ Journey.md`) documented only 4 of the journey's 16 real stages. Every additional stage, field, business rule, and defect discovered during live execution was appended to that file in real time (now extending through AC26), so it now reflects the actual application rather than a partial early draft.
- Roughly 75% of this module's test cases are fundamentally gated behind real, one-time-use human actions (OTP receipt, DigiLocker consent, Liveliness camera capture with a live person) and cannot be meaningfully re-run in an unattended automated suite — each execution consumes a real phone/SMS/DigiLocker/camera session belonging to a real person. This mirrors the established pattern for every other OTP-gated module in this project. The 18 automated test cases cover everything that genuinely can be re-run safely and repeatedly: Mobile Number field validation (never triggers a real OTP send for invalid input) and the four systematic cross-cutting concerns (AC17–AC20) the original story required but had never been tested at all.
- The Minor account type and a non-Joint (Individual) full journey were not exercised live — Joint was deliberately chosen throughout since it also exercises the richer, higher-risk Joint Applicant Details mirror-journey.
- Deleting a Joint Applicant or Nominee via the table's Delete icon was not exercised — destructive against a real, fully-completed live application.
- The final Application Submission (TC-SIL-132) was executed for real on 05-Aug-2026 after a pre-submission cross-verification pass caught and corrected the Spouse Name truncation defect's effect on the actual data. The real application `SAH-1002-798` is now in Submitted status, out of QA's hands and into the bank's normal downstream processing.

## Recommendations

1. **Prioritize `BUG-SILVER-004`** — the Security Code Liveliness identity-verification gap is a genuine security/compliance risk for a banking KYC flow and should be treated as the highest-priority fix from this report, independent of its "Open" status elsewhere.
2. Fix `BUG-SILVER-002`: make "Same as Permanent address" / "Use Existing Address" actually populate all fields (State, City, Pin Code), not just Address Line 1 — currently the feature does not deliver on its own stated function anywhere it appears in the journey.
3. Fix `BUG-SILVER-001`: add real document-content validation (or at minimum server-side image classification) to the PAN/DL/Voter ID/Signature upload points, since extension filtering alone provides no assurance the uploaded file is the claimed document.
4. Fix `BUG-SILVER-003`: either raise the Spouse/Father's Name field's character limit to accommodate realistic full names, or surface a visible max-length warning instead of silently truncating.
5. Update the original user story document to reflect the true 16-stage journey — the gap between documented and actual scope was large enough that anyone relying on the original story alone would materially under-scope this feature.
6. No blockers to go-live for the parts actually tested — every stage exercised (both automated and live-assisted) functioned correctly aside from the defects listed above; the core happy path (mobile verification through to a complete, submittable Summary) works end to end for a Joint account.
